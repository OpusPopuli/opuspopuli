## 6. Regulated-data handling — `ca-personal-information`

**The new columns are numbers about a decision, not content.** `capture_coverage`,
`capture_sharpness`, `capture_detection_confidence`, `capture_crop_fired`,
`capture_frame_width`, `capture_frame_height`. No image, no OCR text, nothing that
narrows down what was photographed.

This property is load-bearing and deliberately defended: a petition page carries the
names, residence addresses and signatures of people who are **not our users** and who
never agreed to anything. Comments on the TypeScript type, the GraphQL DTO and the
migration all state that this must stay numeric, positioned where someone extending it
will read them.

- **No new identifiability.** The columns sit on a row already keyed to `userId`.
  They add no new category and no new linkage.
- **Deletion already covered.** `Document.user` carries `onDelete: Cascade`; account
  deletion removes these columns with the row. Verified in the schema, not assumed.
- **Audit logs.** `capture` is numeric and needs no masking. `ProcessScanInput.data`
  (the base64 image) remains redacted by `pii-masker.ts` — unchanged by this release.
- **Scan images remain unpersisted** (#1075). This release does not weaken that.
- **#1243 fixture reviewed by inspection:** both committed photographs are of a
  **blank** petition form — every signature, name, address and circulator field
  empty; public Attorney-General text only. This was the load-bearing privacy check on
  that PR and it was performed by viewing the images, not by trusting the filename.

**Architectural posture:** inference remains self-hosted within our own trust
boundary. No scan content is sent to a third-party model.

`/op-data-scan` was not run (E-7, carried); the above reflects manual review.

## 9. Deploy prerequisites

**Order is mandatory.**

1. **Backend `v1.25.0` first.** Run migrations (`20260913120000_capture_detection_telemetry`, additive, six nullable columns), then the backend services.
2. **Frontend `frontend-v1.13.0` second**, only once the gateway is serving the new schema.

Deploying the frontend first makes every camera scan send a `capture` field the
gateway does not recognise; the gateway rejects the whole mutation with
`BAD_USER_INPUT` and **every petition scan fails**. This is the same class of trap as
#1057 and it is proven in §4, not inferred.

Layer both compose files on the node, as always:

```
./bin/op-deploy      # already layers docker-compose-prompt-service.yml
```

No manual model pull or other out-of-band step is required for this release.
