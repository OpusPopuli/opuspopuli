## 6. How the corrected defects passed the gates

### 6.1 A $15.5B double-count, invisible behind a 56% rejection rate

Schedule D is a memo schedule restating money itemized on E or F. We summed
all schedules. The error was undetectable while 56% of Schedule E was being
rejected — the two errors partly cancelled. Admitting the rejected rows is
what made the double-count measurable.

The schema comment on `scheduleCode` said Schedule D was a memo schedule all
along. The lesson recorded in the plan: **ask what a column means in the
source before treating it as a fact about the world.**

### 6.2 A disclosure that made the unsupported claim it existed to prevent

`unattributed` counted `payee_name IS NULL` and told readers the recipient
"was not reported". For Schedule D the recipient *is* reported, in
`CAND_NAML` / `BAL_NAME`. 3,521,942 of 3,522,438 no-payee rows were Schedule
D, overstating the figure ~10x platform-wide and far worse per page — Buffy
Wicks read $1,024,518 (200 rows) against a truthful $11,800 (2 rows).

Shipped, then found the next day. Caught by investigating an adjacent bug, not
by any gate.

### 6.3 A routing drop that nearly lost $2.11B silently

Making `payeeName` optional nearly deleted it from the record. The bulk
handler sets a key only for non-blank cells, Zod emits only keys it saw, and
`sortCampaignFinanceItems` discriminates on `"payeeName" in rec` — so a blank
payee produced **no key**, matched no route, and vanished with no counted
reject. The first regression test missed it by using `payeeName: ""` (a
present key). The fix is one load-bearing line restating the key, and the test
now `delete`s it and asserts through the real router.

**This is the failure mode this release should be remembered for:** an
optional field can lose rows at *routing*, where nothing counts a reject,
rather than at validation, where something does.
