# #1383 — a secondary detail page, so a scraped bio replaces an invented one

**Issue:** [#1383](https://github.com/OpusPopuli/opuspopuli/issues/1383).
Related: #1381, #1382, #596. Evidence:
`docs/evals/2026-10-19-representatives-gold.md`.

## Problem

Representative biographies are generated by an LLM from four structured
fields — `Name / Jurisdiction / District / Party` — so **71.1% of bio claims
are unsourced**, and measurably wrong: we publish that Aguiar-Curry holds a
UC Davis degree and was a Yolo County Supervisor residing in Davis, where her
official page says San Jose State, first female mayor of Winters, residing in
Winters.

The biography exists, publicly, at a URL **we already store**.
`contactInfo.website` is extracted and populated for all 120 state reps, and
the bio sits one path segment further on:

| | |
|---|---|
| detail page archived today | `assembly.ca.gov/assemblymembers/04` — committees, offices, counties |
| biography | `a04.asmdc.org/biography` — 2,492 chars, extracts cleanly |

## Why this is worth more than grounding the prompt

`BioGeneratorService.enrichBios()` filters to reps with no bio:

```ts
const candidates = reps.filter((r) => !r.bio || r.bio.trim() === "");
```

and marks any pre-existing bio `bioSource = 'scraped'`. **Generation only runs
when the scrape produced nothing.** So extracting the real biography does not
merely ground the model — it removes the model from the path: verbatim
official text, `bioSource: 'scraped'`, and the `AI-generated` badge correctly
disappearing. `bioNoisePatterns` already exists in the region schema for this
path; it is simply never reached today.

That also shrinks #1381 to the reps whose bio genuinely cannot be scraped.

## Decisions

### D1. A new `secondaryDetail` capability, not a repointed `detailUrl`

`detailFields` is `Record<string, string | StructuredFieldConfig>` applied to
the single `detailUrl`. Pointing that at the bio page would lose committees
and offices — which the roster page genuinely carries and which score **90%
recall** today. Trading a measured 90% for an unmeasured bio is not a trade.

So add a second, optional per-item hop:

```json
"secondaryDetail": {
  "urlFrom": "contactInfo.website",
  "urlSuffix": "biography",
  "fields": { "bio": ".entry-content" }
}
```

`urlFrom` names a field the **primary** detail extraction already produced, so
no new discovery is needed — only a fetch. Generic on purpose: committees and
bills want the same shape later.

### D2. It may only fill fields that are absent

A secondary page can set a field the primary left empty; it can never
overwrite one the primary produced. Rationale: the primary page is the
authoritative roster record, and a silent clobber from a looser secondary
selector is the kind of regression that reads as "the data changed" rather
than "we broke it". Asserted in a test.

### D3. Failure is isolated and never costs the primary enrichment

A secondary fetch that 404s, times out, or matches nothing must leave the
item exactly as the primary enrichment left it, and warn. The same reasoning
as `runPostSyncLinkers`: a bio we could not fetch must not discard committees
we did.

### D4. Provenance: `sourceVersionId` stays on the primary page, and we say so

`enrichSingleItem` stamps `item.sourceVersionId` from the primary fetch
(#1306 — per item, not per run). The secondary page is a **different**
`source_version` row, so one id cannot honestly describe both.

This change does **not** repoint `sourceVersionId` at the secondary page,
because committees and offices come from the primary and would then be
misattributed. The secondary page **is** archived — `fetchDetailContent`
carries the `archive` context, so its bytes and hash are preserved and
identifiable by URL — but the rep row will not point at it.

**That is a real limitation, recorded rather than hidden**, and per-field
provenance is filed separately. Mis-stating where a biography came from would
be a worse defect than not stating it, given #1279/#1283 exist to bind an
analysis to the text it cites.

### D5. Fetch volume is bounded by the existing caps

A secondary hop at most doubles detail fetches. It reuses `MAX_DETAIL_PAGES`
(500) and `DETAIL_FETCH_DELAY_MS` (500ms) rather than introducing a second
budget, so a misconfigured source cannot quietly double the crawl.

### D6. Assembly Democrats only, this change

| group | reps | route |
|---|---:|---|
| Assembly Democrats (`asmdc.org`) | 60 | this change |
| Assembly Republicans (`asmrc.org`) | 20 | **blocked** — Cloudflare managed challenge |
| Senate | 40 | not this issue — their website *is* the archived page; #1382 |

On the Republican side: `asmrc.org` serves a Cloudflare managed challenge, and
**even `/robots.txt` is behind it**, so the operator's crawl policy cannot be
read. No evasion will be built — not a headless browser aimed at the
challenge, not UA rotation. The legitimate route found is the **Internet
Archive**, which serves its own lawful copy and verifiably holds these pages
(3,962 chars of Hadwick's real biography from a 2026-09-01 snapshot). It needs
dynamic snapshot resolution via `archive.org/wayback/available`, which is a
different fetch shape, so it is **a follow-up, not this change**.

Until then those 20 keep an AI-generated bio, and the disclosure should say
the source blocks ingestion — the owner's call, recorded in
`docs/evals/2026-10-19-representatives-gold.md`.

## Subtasks

1. **Types** — `SecondaryDetailConfig` and `secondaryDetail?` on
   `DataSourceConfig` in `packages/common`.
2. **Crawler** — in `detail-crawler.service.ts`, after primary extraction:
   resolve the URL from `urlFrom` + `urlSuffix`, fetch via the existing
   `fetchDetailContent` (so it is archived), apply `fields`, merge per D2,
   isolate failures per D3.
3. **Schema** — `secondaryDetail` in `opuspopuli-regions`
   `schema/region-plugin.schema.json`.
4. **Config** — `secondaryDetail` on `dataSources[6]` (Assembly) in
   `regions/california/california.json`.
5. **Tests** — absent-only merge (D2), failure isolation (D3), URL joining
   with and without a trailing slash, a missing `urlFrom` field skipping
   cleanly. Mutation-verify D2 and D3.
6. **Publish + pin** — `@opuspopuli/regions` release, pinned in **both**
   `apps/backend` and `packages/region-provider` (#1328: the region service
   resolves from `region-provider`, so bumping only the backend ships the old
   config with no error anywhere).

## Acceptance

- [ ] A rep whose `contactInfo.website` resolves gets `bio` from
      `{website}/biography`, and `bioSource` becomes `scraped`
- [ ] Committees, offices and counties are unchanged — the 90% recall measured
      in the gold set does not move
- [ ] A secondary fetch failure warns and leaves the item as the primary left
      it (mutation-verified)
- [ ] The secondary page appears in `source_versions`
- [ ] `grep` of the resulting bios finds none of the template phrases
      ("community organizer" in 49 of 125 today)
- [ ] Verified on Aguiar-Curry specifically: the bio names Winters, San Jose
      State and the walnut orchard, and no longer claims UC Davis or a Yolo
      County supervisorship

## Risks

| risk | mitigation |
|---|---|
| Secondary selector too loose, pulls nav/boilerplate | `bioNoisePatterns` already exists for exactly this; verify extracted text per rep before a corpus run |
| `/biography` is not universal across all 60 | Verified on `a04`, `a53`, `a10`. A 404 is isolated (D3) and the rep keeps a generated bio |
| Doubling fetches lengthens the reps sync | D5 reuses existing caps; reps is 120 items, not a large crawl |
| Overwriting good primary data | D2, asserted and mutation-verified |
| Provenance misattribution | D4 — explicitly not repointed, limitation recorded, follow-up filed |
| Config shipped but not pinned in `region-provider` | Subtask 6, and #1328 is the recorded precedent for exactly this failure |

## What implementation found that the plan did not

**1. D2 was already the existing behaviour.** `mergeContent` skips keys the
item already holds (`if (!item[key])`). So the absent-only merge needed no new
code — reusing it is both less code and un-driftable. Still mutation-verified,
because "it happens to be true today" is not a guarantee.

**2. The primary path dumps page text into `bio` when selectors miss, and that
must NOT be inherited.** `extractWithPlan` falls back to a main-content text
dump, and `getDefaultTextFields("representatives")` is `["bio"]`. So a roster
page whose selectors all miss stores its nav and footer *as the biography* and
marks it `bioSource: 'scraped'`. That is #658's "junk bios" mechanism, found
here by a test failing for the wrong reason.

The secondary hop therefore calls `extractContent` directly — selector-only,
no fallback — and warns on a miss. A biography is the last field that should
ever be filled by a text dump.

**3. The obvious selector is wrong, and only live pages showed it.**
`.field--name-body` looks right and fails: it matches **three** elements on
`a04.asmdc.org/biography` and the **first is empty**.
`article .node__content .field--name-body` returns exactly one correct match
on all three pages tested (a04 1,922 / a53 4,594 / a10 2,092 chars). Verified
against fetched pages rather than reasoned about.

**4. An empty extraction slipped past the miss check.** Following from (3): a
keys-only test sees `{ bio: "" }`, counts it a hit, warns about nothing, and
`mergeContent` then silently skips the empty value — field unset, no
diagnostic. Empty and whitespace-only values are now filtered before the
check, with a regression test naming the a04 case that produced it.

**5. `additionalProperties: false` on `DataSourceConfig`.** The schema had to
change or the config would have failed validation — the regions repo's
`validate-configs.spec.ts` is the gate that would have caught it, and does
(515 tests pass with both changes).
